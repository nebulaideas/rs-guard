# v1.7.0 — GitHub-native UX

**Status:** Planned  
**Milestone:** [v1.7.0 - GitHub-native UX](https://github.com/nebulaideas/rs-guard/milestone/3)  
**Theme:** Make rs-guard feel like a first-class GitHub review bot — inline comments, branch-protection Check Runs, robust structured verdicts, and resilient review submission.

Builds on v1.6 foundations (larger/cleaner diffs, path filters, JSON output, outbound redaction). Prefer landing v1.6 security/size work first where dependencies exist; Check Runs and body truncation can proceed independently.

---

## Goals

1. Post findings as **inline review comments** (path + line) when the model provides them, with a prose overview comment.
2. Optionally publish a **Check Run** so branch protection does not depend on `APPROVE` / `REQUEST_CHANGES` permissions.
3. Prefer **structured JSON verdicts** (with text metadata fallback) to reduce truncation/parser drift.
4. **Never fail** a useful review solely because the body exceeds GitHub's 65k character limit.

---

## Design decisions

These decisions are locked for v1.7 and must be reflected in acceptance criteria.

| Topic | Decision |
|---|---|
| Structured findings | **Opt-in** via `--findings` / `RS_GUARD_FINDINGS` / `findings = true` in TOML. |
| Inline comments | **Opt-in** via `--inline-comments` / `RS_GUARD_INLINE_COMMENTS` / `inline_comments = true`. Implies `--findings`. |
| JSON mode | **Embedded JSON only.** rs-guard does not use provider-native `response_format: json_object`. The model emits a prose overview followed by a `[RS_GUARD_VERDICT_FINDINGS]` marker and a JSON array. |
| Counts source | When findings are present, derive `critical`/`security`/`important`/`suggestion` counts from the findings array. Otherwise fall back to the existing metadata block. |
| Unmappable findings | Findings that cannot be mapped to a diff position are appended to the overview body rather than dropped. |
| Check Runs | Created **in addition to** the PR review. A Check Run failure does not fail the pipeline; it is logged as a warning. |
| Check Run conclusions | `APPROVE` → `success`; `REQUEST_CHANGES` → `failure`; `COMMENT` → `neutral`. |

## Permissions note

- Review events: `pull-requests: write` (existing).
- Check Runs: `checks: write` (new; must be documented in bot setup).
- `GITHUB_TOKEN` often cannot `APPROVE` / `REQUEST_CHANGES` — Check Runs + `COMMENT` fallback remain important.
